# Internationalization (i18n)

This file covers two layers:

1. **UI-string i18n** (application chrome — buttons, labels, modals, toasts) — powered by
   `next-intl`. See [UI String Translation](#ui-string-translation) below.
2. **Content localization** (blog posts, articles) — per-locale markdown + generated indexes.
   Covered from [URL Structure](#url-structure) onward.

All component-reachable UI strings are extracted into the message catalog — the
external/marketing surface (landing, auth, settings, premium, modals, toasts, SEO metadata) and
the app-internal feature areas (coding-exercise, lesson, quiz-card, challenge, dashboard,
projects, guides, build, unsubscribe, video-exercise, achievements/challenges pages, shared UI
components). The remaining hardcoded English lives in plain-`.ts` files with no hook context —
see [Not yet localized (deferred)](#not-yet-localized-deferred). The original area-by-area sweep
is documented in `.context/i18n-ui-strings-plan.md` (the runbook).

## UI String Translation

UI strings use **next-intl** (v4) in "without i18n routing" mode: next-intl itself doesn't do URL
routing, but `resolveLocale` derives the locale per the precedence below so public pages are
URL-driven and app pages are user-driven.

- **Library wiring**: `next.config.ts` applies `createNextIntlPlugin("./lib/i18n/request.ts")`.
- **Request config**: `lib/i18n/request.ts` fetches the resolved locale's catalog from the
  content-hashed cache tree (see [Catalog delivery](#catalog-delivery) below).
- **Message catalog**: `messages/en.json` (canonical) and `messages/hu.json`. `hu` falls back to
  English per the `?? en` convention. The two files are structurally identical (same key tree).
- **Key typing**: `global.d.ts` augments next-intl's `AppConfig.Messages` so message keys
  autocomplete and typecheck against `messages/en.json` (a type-only import, erased at compile —
  it does not bundle the catalog).

### Catalog delivery

UI catalogs are **fetched at runtime from the content-hashed cache tree** (R2 in production),
never bundled — the worker bundle does not grow with the locale count, and translation updates
don't require a worker redeploy.

- **Generation**: `scripts/generate-messages-cache.js` (wired into `dev` and `build`, with a
  `messages-cache:watch` variant) reads `messages/{locale}.json` and writes
  `public/static/i18n/app/{locale}/messages-{hash}.json`, a pointer
  `public/static/i18n/app/{locale}/current.json` for each non-default locale, plus the hash
  manifest `lib/generated/messages-hashes.ts` (locale -> hash). A missing `en.json` is a hard
  error, never an empty manifest. The hashed catalogs are uploaded to R2 immutably by
  `static:upload`; in dev the files are served from `public/` by the Next dev server.
- **Loader**: `lib/i18n/catalogLoader.ts` (`createCatalogLoader`, unit-tested in
  `tests/unit/lib/i18n/catalogLoader.test.ts`) fetches `assetsUrl(appMessagesPath(locale, hash))`
  with a promise cache keyed `${locale}:${hash}`, one retry on failure, then throws. A rejected
  fetch is evicted from the cache so a later call retries instead of caching the failure.
- **Server (SSR)**: `lib/i18n/request.ts` builds a module-scope loader over the server-side
  `assetsUrl` (reused across requests on a warm isolate); a failed load fails the request.
- **Client**: `ClientLocaleProvider` builds the same loader over the client `assetsUrl` for
  client-side locale swaps.
- **No bundled fallback (deliberate)**: a catalog that cannot load fails the request loudly —
  never a silent English render.

### Runtime hash resolution (pointers)

Translations are authored in a separate `i18n` repo that publishes its own artifacts to R2. That
repo has to be able to ship a translation without the front-end rebuilding, so the hash naming a
catalog is resolved at runtime rather than compiled into the worker. `lib/i18n/catalogPointer.ts`
(`createHashResolver`, unit-tested in `tests/unit/lib/i18n/catalogPointer.test.ts`) is the one
place that happens.

- **The pointer** is a small MUTABLE object at a stable path,
  `/static/i18n/{namespace}/{locale}/current.json`, holding `{ "hash": "..." }`. The hashed
  artifact it names is unchanged and still immutable. Publishing a translation is rewriting the
  pointer.
- **English has no pointer.** Its hash comes from the compiled manifest and its catalog ships with
  the worker deploy, atomically, so the code and the copy it renders go live together. The
  default-locale render path performs zero runtime lookups, which matters because production
  serves English only.
- **One writer per pointer object.** The i18n repo owns every non-English pointer on R2; the
  front-end's `static:upload` excludes `*/current.json` entirely, so the two publishers cannot
  lose each other's writes. The front-end generators still write pointers into `public/`, because
  otherwise `next dev` could not serve a non-English locale at all.
- **Caching**: the pointer is uploaded with a short TTL plus a long `stale-while-revalidate`, so
  the steady state is an edge cache hit and a slow origin never blocks a render. There is
  deliberately no second, in-process cache of a resolved hash — that would stack an invisible
  staleness window on the chosen one. Concurrent resolutions for a locale do share one in-flight
  pointer fetch, dropped as soon as it settles.
- **Failure is loud**: a missing pointer, a malformed one, or one naming an artifact that is not
  there all throw. There is no fallback to a compiled non-English hash and no fallback to English.
- **Discovery is still compile-time.** The pointer answers "what hash", never "what locales".
  Which locales exist comes from `ALL_LOCALES` in `lib/locales.ts` and nowhere else.

Wired to pointers today: the app UI catalog (`lib/i18n/catalogLoader.ts`) and the curriculum level
catalog (`lib/api/level-meta.ts`). The remaining hash manifests in `lib/generated/` (exercise
messages, interpreter messages, curriculum copy, badges, concepts, content, exercises) are still
resolved purely at build time.

### Curriculum catalogs (not app chrome)

Curriculum-owned strings never live in `messages/*.json` — they are authored beside the
curriculum and delivered through the same content-hashed cache tree:

- **Exercises**: `curriculum/src/exercises/{slug}/locales/{locale}/translation.json` and the shared
  family catalogs `curriculum/src/exercise-categories/{family}/locales/{locale}/translation.json`,
  emitted by `scripts/generate-exercise-cache.js`.
- **Levels**: `curriculum/src/levels/locales/{locale}/translation.json` — the level display titles,
  keyed by level id (`{ "using-functions": { "title": "Using Functions" } }`). Emitted by
  `scripts/generate-levels-i18n-cache.js` to `public/static/i18n/levels/{locale}/messages-{hash}.json`
  plus the manifest `lib/generated/level-message-hashes.ts`. Fetched by
  `lib/api/level-meta.ts` (`fetchLevelMessages`) and consumed through the
  `useLevelTitles()` hook (`lib/i18n/useLevelTitles.ts`). The level registry
  (`curriculum/src/levels/*.ts`) remains the source of truth for level ids and canonical English
  titles; `tests/unit/levelMessages.test.ts` holds the `en` catalog in lockstep with it and enforces
  key-tree parity across locales.
- **Interpreters**: `interpreters/src/{language}/locales/{locale}/translation.json`, emitted by
  `scripts/generate-interpreter-i18n-cache.js`.

All three follow the same miss behaviour: a locale with no catalog resolves to `{}` and the key (or
level id) surfaces verbatim — a loud canary, never a silent English fallback. Untranslated entries
in a catalog that does exist are marked with the `�` (U+FFFD) placeholder.

### Locale resolution model

The guiding split is **cacheable/public pages resolve locale from the URL; auth-gated per-user
pages resolve from the user's preference** (the locale fields on `/internal/me`, combined by
`resolveUserLocale()` — see [User locale from the API](#user-locale-from-the-api)). The
`NEXT_LOCALE` cookie is an optimistic, FE-owned SSR hint that self-heals from `/me` — it is never
the source of truth.

- **Server resolution** (`lib/i18n/resolveLocale.ts`), precedence:
  1. Explicit URL locale segment — surfaced by `middleware.ts` as the `x-url-locale` request header
     (`URL_LOCALE_HEADER`). Middleware always sets or clears it from the trusted path, so it can't be
     spoofed. Wins for everyone, keeping public/cacheable pages deterministic per URL.
  2. Otherwise, if the auth-presence cookie exists (possibly-logged-in), the `NEXT_LOCALE` cookie
     (the optimistic seed).
  3. Otherwise (anon, naked URL) `DEFAULT_LOCALE`. The `NEXT_LOCALE` cookie is intentionally ignored
     here so anon cacheable pages stay deterministic.
- **Provider + client correction** (`components/i18n/ClientLocaleProvider.tsx`): `app/layout.tsx`
  resolves `getLocale()`/`getMessages()` server-side and passes them as `initialLocale`/
  `initialMessages`. The provider renders that seed for first paint (so external/anon SSR is
  unaffected), then watches `resolveUserLocale(user)` from the auth store. When the authoritative locale differs
  from the seed it dynamic-imports that catalog and swaps in place. "Swap pending"
  (`authoritative !== active`) is derived synchronously and the provider renders `LoadingJiki` during
  a swap, so the app never paints in the wrong locale; a failed catalog load is recorded so the swap
  settles instead of spinning forever. For anon users `user` is null, so no swap ever occurs.
- **Cookie writes** (`lib/i18n/localeCookie.ts` `setLocaleCookie`): `authStore.setUser` mirrors the
  authoritative locale into `NEXT_LOCALE` (covers `/me`, login, signup, confirm), resolved through
  the same `resolveUserLocale()` the provider uses so the cookie cannot disagree with what renders.
  The cookie can be stale but never lastingly wrong, since `/me` re-seeds it.
- **`<html lang>`**: set server-side in `app/layout.tsx` from the seed; `ClientLocaleProvider`
  corrects `document.documentElement.lang` after a swap.
- **Signup seeding** (`lib/i18n/detectSeedLocale.ts`): `SignupForm` sends `locale` inside the `user`
  registration params **only when the user is on a locale page** (a non-default `useLocale()`);
  otherwise it omits the field and the backend falls back to the request's `Accept-Language` header
  (the same data `navigator.languages` would give, read once server-side) then the default. The
  backend persists a supported value and ignores unsupported ones.

### Backend contract

- `/internal/me` returns three locale fields on `user` — see
  [User locale from the API](#user-locale-from-the-api).
- `POST /auth/signup` accepts an optional `user.locale` and ignores unsupported values.
- `PATCH /internal/settings/locale` persists an explicit change (no in-app switcher UI yet — see
  deferred). It is what sets `explicit_locale`.

### User locale from the API

`/internal/me` returns three locale fields on `user`:

- `explicit_locale` — the locale the user deliberately chose, or `null` if they never have.
- `locale` — the persisted account preference (required, never null for a real row: the backend
  lazy-backfills it from `Accept-Language` on first read). `User.locale` is typed required.
- `locales` — every locale the API parsed out of the browser's `Accept-Language` string that it
  recognised as valid, in the browser's own preference order.

`resolveUserLocale()` (`lib/i18n/userLocale.ts`) is the single resolver, in precedence order
`explicit_locale` → first served entry of `locales` → `locale`. It returns `undefined` when none of
them yields a served locale, so callers keep whatever locale they already resolved rather than being
forced back to English. `explicit_locale` wins outright: a deliberate choice must not be overridden
by what the browser happens to be asking for, or switching language would silently revert on the
next load.

`locales` is read defensively rather than trusted from the type, so an API that has not shipped it
yet degrades to `locale` instead of throwing.

Two callers share it, which is the point: `ClientLocaleProvider` picks the authoritative UI locale
with it, and `authStore.setUser` mirrors that same resolved value into the `NEXT_LOCALE` cookie.

### Using translations

- Server components: `const t = await getTranslations("namespace")` from `next-intl/server`.
- Client components: `const t = useTranslations("namespace")` from `next-intl`.
- Rich text: `t.rich("key", { strong: (c) => <strong>{c}</strong> })`.
- Interpolation/plurals: ICU syntax in the JSON (`{name}`, `{count, plural, ...}`).

Reference implementation: `components/layout/ExternalFooter.tsx`.

Key-naming convention: namespace = feature folder; dot-nested to mirror the component tree;
camelCase leaf keys describing the role (not the English text). Shared strings live under `common.*`.

### Shared vs duplicated strings

Two strings with the same English text are **not** automatically the same message — context can
change the translation. The rule:

- **Share** (one key under `common.*`) when the string has one meaning everywhere regardless of
  surrounding UI: progress states (`common.processing`, `common.verifying`, `common.sending`,
  `common.loading`), generic dialog buttons (`common.continue`, `common.close`, `common.cancel`,
  `common.confirm`, `common.reloadPage`), generic error-recovery actions (`common.retry`,
  `common.tryAgain`), the price unit (`common.perMonth`), and form validation
  messages (`common.validation.*`). The Premium benefit title/description pairs shared by the
  settings upsell and benefits views live under `premium.benefits.*`; strings shared by the two
  2FA forms live under `auth.twoFactor.*`.
- **Duplicate deliberately** when the same English text plays different roles: e.g.
  `settings.cancelSectionPanel.cancel` ("Cancel" = cancel the subscription) is a different message
  from `common.cancel` ("Cancel" = dismiss the dialog); nav labels, headings, and page titles stay
  per-feature even when they coincide with a button label.

When merging or adding shared keys, keep `en.json` and `hu.json` structurally identical.

### ICU, not string concatenation

Never split a sentence across multiple keys (`fooPrefix` + `fooSuffix`) to inject markup, links,
or dynamic values — word order differs across languages and whitespace-padded fragments are
fragile. Use a single ICU message:

- Inline markup/styling: `t.rich("key", { highlight: (c) => <span className={...}>{c}</span> })`
- Links: `t.rich("key", { link: (c) => <Link href={...}>{c}</Link> })`
- Embedded components (e.g. live prices): self-closing tags — `t.rich("key", { price: () => <PremiumPrice /> })`
- Interactive chunks: a tag may render a control, not just markup. The locale banner is the worked
  example — `layout.localeBanner.message` is one sentence whose `<link>` chunk is the switch link
  and whose `<dismiss>` chunk is the close button, so the button's accessible name is the translated
  copy and a translator can reorder the whole sentence. The client bar
  (`components/i18n/LocaleBannerBar.tsx`) takes the rendered sentence as `children` and exposes its
  dismiss action through a context that `LocaleBannerDismiss` consumes.
- Values: `{name}` interpolation; counts: ICU `{count, plural, one {...} other {...}}` (never a
  hand-rolled `count === 1 ? t("singular") : t("plural")`).

`tests/unit/messages.test.ts` guards the catalogs: every message must parse as valid ICU, the
`en`/`hu` key trees must be identical, and no message may have leading/trailing whitespace
(whitespace-padded fragments are how concatenation bugs sneak back in).

### Language names

`languageName(locale, inLocale)` (`lib/i18n/languageNames.ts`) writes a language's name using
`Intl.DisplayNames`. There is no authored catalog of language names: one would need an entry for
every locale in every other locale, so it would grow as the square of the locale list and go stale
silently each time a locale is added. ICU already ships that data, including region-suffixed ids
like `es-419` and `pt-BR`, and falls back to the locale code itself when it has no name.

### Building locale-aware links

Never hardcode internal navigation paths (`href="/auth/login"`, `router.push("/blog")`). They
would always resolve to the default-locale (naked) URL, so a `hu` user clicking them drops back to
English. Instead use the route helpers in `lib/i18n/`, which are the exact inverse of the
middleware's `resolveLocaleRouting` and share its single source of truth (`LOCALIZABLE_BASES` in
`lib/i18n/config.ts`):

- **Core primitive**: `localePath(path, locale)` (`lib/i18n/routes.ts`) applies the URL rule
  (default locale naked, others `/<locale>`-prefixed) but **only** for localizable bases. Routes
  without a `[locale]` tree (the auth-gated `/dashboard`, `/settings`, `/lesson`, …) stay naked in
  every locale, matching the middleware. It preserves query/hash and is idempotent.
- **Named helpers**: `makeRoutes(locale)` returns Rails-style builders (`routes.authLogin()`,
  `routes.blogPost(slug)`, `routes.premium()`, …) — the one canonical place each path string lives.
- **Ambient wrappers** (what call sites use, so nobody threads `locale` through props):
  - `useLocaleRoutes()` (`lib/i18n/useLocaleRoutes.ts`) — reads `useLocale()`. Works in client
    components **and** sync-rendered server components (pair it with `useTranslations()`).
  - `getLocaleRoutes()` (`lib/i18n/getLocaleRoutes.ts`) — `await`s `getLocale()`; for async server
    components (pair it with `getTranslations()`).

Rule of thumb: use the routes wrapper matching your translations API — `useTranslations` ↔
`useLocaleRoutes`, `getTranslations` ↔ `getLocaleRoutes`. Absolute external URLs
(`https://jiki.io/...`) are left as-is. Query-carrying links compose by using the helper as the
base, e.g. `buildUrlWithReturnTo(routes.authSignup(), returnTo)`.

### Catalog namespaces

Top-level namespaces in `messages/en.json` (and `hu.json`, which is structurally identical):
`common`, `layout`, `auth`, `settings`, `toasts`, `premium`, `roadmap`, `landing`, `seo`, `modals`,
`misc`, `concepts`, `build`, `codingExercise`, `lesson`, `quizCard`, `videoExercise`, `challenge`,
`challenges`, `dashboard`, `projects`, `guides`, `unsubscribe`, `achievements`, `subscription`,
`blog`, `articles`, `checkout`. `blog.*` and `articles.*` back the public blog and help-center
chrome (page headers, post/article bylines, CTA blocks, search, tag filter); the two share a body
of near-identical CTA copy but keep separate keys so each surface translates independently.
`checkout.*` holds the checkout-return decline fallback.
`subscription.tiers.*` holds the membership-tier display copy (name/description/feature lists)
shared by the settings subscription UI and the subscription modals. `seo.*` backs page
`generateMetadata` (titles/descriptions); `toasts.*` covers toast messages, fired by key via the
`lib/toast.tsx` helpers from any context (components, stores, plain classes); `challenge` is the
single-challenge screen while `challenges` is the listing pages;
`unsubscribe` is the preference-management UI while `auth.unsubscribe` is the one-click token flow.

### Never localized (by design)

- **`/dev` and `/test` routes** and the components that exist only for them: development-only
  tooling, never shown to students. Do not extract their strings into the catalog.
- **`app/global-error.tsx`** — replaces the entire HTML tree when the app crashes hard, so it must
  render with ZERO loadable dependencies (no `NextIntlClientProvider`, no catalog import, no fetch).
  Its strings therefore live in an inline `COPY` dictionary keyed by locale inside the file, and are
  deliberately kept out of `messages/*.json`. A tiny dependency-free `resolveGlobalErrorLocale()` in
  the same file mirrors `resolveLocale`'s precedence client-side (URL locale segment → `NEXT_LOCALE`
  cookie → default), and `<html lang>` follows it. Adding a locale here is a manual, per-locale edit;
  the translation repo knows about this deliberate exception.

### Not yet localized (deferred)

The chrome sweep is complete: every component-reachable UI string resolves through the catalog.
What remains deferred is out of that sweep by design:

- **Plain-`.ts` strings with no hook/await context**: none remain in the chrome surface. Anything
  fired from a plain (non-hook) context uses a keyed indirection so the copy still resolves in the
  right locale — toasts go through the `lib/toast.tsx` helpers (`toastError`/`toastSuccess`/…),
  which resolve when the toast paints inside the provider (see `.context/toasts.md`). The
  coding-exercise editor + test-runner layer (CodeMirror gutter/tooltip DOM in
  `ui/codemirror/extensions/*` and the scenario runners in `lib/test-runner/*`, which build
  DOM/`errorHtml` outside React) resolves its `codingExercise.*` keys through a module-level
  registry, `components/coding-exercise/lib/i18n/editorMessages.ts`: `useExerciseLoader` seeds it
  once per load via `setEditorMessages` from its `useTranslations("codingExercise")` translator, and
  the plain modules call `editorMessage(key, values)`. English defaults are baked in so behaviour is
  correct before seeding and in unit tests that never mount the provider. A string that genuinely
  needs translating from a plain module should adopt one of these pass-a-key patterns rather than
  hardcoding English.
- **Content** (out of scope by design): blog/article/concept bodies, exercise/curriculum text,
  `components/testimonials/testimonials.json` (the `/testimonials` page), and the blog/articles
  `[locale]` routing.
- **Landing-page testimonials + hero marquee** are editorial content, not chrome, so they live in
  the content package (`content/src/testimonials/{locale}.json`), not the message catalog. They are
  delivered synchronously for SSR via `getTestimonials(locale)` from `@/lib/content` (baked into
  `content-meta-server.json`), so the landing page stays server-rendered and cacheable. There are no
  `landing.testimonials.*` or `landing.hero.marquee.*` catalog keys. See `.context/content.md`.
- **`date-fns` relative time**: the achievements badge label ("Earned 3 days ago") localizes its
  chrome words via `achievements.badge.*`, but the relative-time phrase itself comes from
  `formatDistanceToNow` with date-fns' default English locale (`getBadgeDateInfo` in
  `app/(app)/achievements/lib/badgeUtils.ts` returns the raw distance). Fully localizing it means
  passing a per-locale date-fns locale; deferred.
- **In-app language switcher**: no settings UI to change locale yet (and no live catalog swap on a
  settings change). `settingsStore.updateLocale` exists but is unused. Deferred.

## Locale Configuration

Locales are defined in `lib/locales.ts`:

- `ALL_LOCALES` — every locale the codebase knows about; the `Locale` type and message
  catalogs (`messages/*.json`) are authored against this set.
- `SUPPORTED_LOCALES` — the locales actually served in this environment. Production ships
  `en` only; `next dev` serves the full set.
- `DEFAULT_LOCALE` — `en`.

## URL Structure

- **Default locale (English)**: Served at naked URLs (`/blog`, `/help`)
- **Non-default locales**: Served at locale-prefixed URLs (`/hu/blog`, `/hu/help`)
- **English locale prefix**: Redirects to naked URLs (`/en/blog` → `/blog`)
- **Miscased locale segments**: 308 to the canonical casing (`/HU/blog` → `/hu/blog`,
  `/pt-br/x` → `/pt-BR/x`). URL paths are case-sensitive, so the canonical BCP-47-cased slug
  is the only URL that serves content; `resolveLocaleRouting` normalizes known locale
  segments only (never a blanket lowercase). A miscased default-locale prefix goes straight
  to the naked URL in a single hop (`/EN/blog` → `/blog`).
- **Region suffixes**: a slug carries a region suffix only when the language has more than
  one live content variant (`/es-ES/`, `/es-419/`, `/pt-PT/`, `/pt-BR/`); single-variant
  languages stay bare (`/hu/`).

## Multi-Variant Languages (Spanish, Portuguese)

Some languages ship more than one content variant. The canonical ids (matching the API's
`I18n::SUPPORTED_LOCALES`) are `es-ES` (Peninsular), `es-419` (neutral Latin American),
`pt-PT` and `pt-BR`. These are not yet in `ALL_LOCALES` — the machinery below is already
built and tested for them (`tests/unit/lib/i18n/futureLocales.test.ts` runs it against the
future set), so going live is just the "Adding a New Locale" steps.

The casing is load-bearing, not cosmetic: the locale id is also the catalog filename
(`messages/pt-PT.json`), the content filename (`pt-PT.md`), the curriculum locale directory
(`locales/pt-PT/`) and the URL segment. The cache-generation scripts derive the locale from the
filename verbatim, so a locale id that disagrees with its files in case resolves to nothing — and
`resolveLocaleRouting` would 308 the canonical URL away to the miscased one. Anywhere a locale id
is written by hand (`TranslatathonBanner`'s copy table, for instance) must use the canonical casing.

- **Accept-Language negotiation** (`LANGUAGE_VARIANTS` in `lib/i18n/localeBanner.ts`):
  Chromium sends `es-419` directly but Firefox/Safari send country codes (`es-CL`, `es-AR`),
  so each tag resolves exact-first, then collapses by region (bare `es` → `es-419`, region
  `ES` → `es-ES`, any other region → `es-419`; bare `pt` → `pt-BR`, unlisted pt regions →
  `pt-PT`). This mirrors the API's `User::DetermineLocale` — keep the two tables in sync.
  The same resolution drives the locale banner and the anonymous cache bucket.
- **hreflang** (`hreflangLocale` in `lib/seo/alternates.ts`): Google only accepts
  ISO-3166-1 alpha-2 regions, so `es-419` (a UN M.49 code) collapses to generic `es` in
  hreflang keys. URLs, `<html lang>` and everything else keep the full internal id. Page
  metadata and the sitemap share `alternateLanguages`, so the mapping lives in one place.

## Everything Locale-Varying Is Fetched

The rule: **if a piece of content varies by locale, it is a content-hashed artifact, its hash
resolves through the pointer, and the app fetches it.** Server component or client component is an
implementation detail, not grounds for an exception.

| Namespace             | Artifact                                                            | Published by |
| --------------------- | ------------------------------------------------------------------- | ------------ |
| App UI catalog        | `/static/i18n/app/{locale}/messages-{hash}.json`                    | i18n         |
| Curriculum copy       | `/static/i18n/curriculum/{locale}/messages-{hash}.json`             | i18n         |
| Badges                | `/static/i18n/badges/{locale}/messages-{hash}.json`                 | i18n         |
| Levels                | `/static/i18n/levels/{locale}/messages-{hash}.json`                 | i18n         |
| Exercise catalogs     | `/static/i18n/exercises/{slug}/{locale}/messages-{hash}.json`       | i18n         |
| Interpreter catalogs  | `/static/i18n/interpreter/{language}/{locale}/messages-{hash}.json` | i18n         |
| Exercise prose index  | `/static/exercises/{locale}/index-{hash}.json`                      | i18n         |
| Exercise instructions | `/static/exercises/{slug}/{locale}/prose-{hash}.json`               | i18n         |
| Concept pages         | `/static/concepts/{slug}/{locale}/content-{hash}.html`              | i18n         |
| Posts and episodes    | `/static/content/{kind}/{slug}/{locale}/content-{hash}.html`        | i18n         |
| Concept index         | `/static/concepts/{locale}/index-{hash}.json`                       | front-end    |
| Content metadata      | `/static/content/meta/{locale}/index-{hash}.json`                   | front-end    |
| Search indexes        | `/static/content/search/{type}/{locale}/index-{hash}.json`          | front-end    |

Nothing in that table is bundled. Every row is fetched, and every non-English hash comes from a
pointer, so a locale published after this build was made is reachable.

**Indexes are split, exactly as the exercise cache is.** An index mixes translated copy with
structure, so it becomes two artifacts on their real keys. A concept's hierarchy, order, icon and
exercise links come from English config and are the same in every language, so the front-end
publishes one object for all of them; its title, description and per-locale content hash are
translated, so i18n publishes those per locale. A post's date, author, cover image and
featured/listed/premium/order flags are the structural half; its title, excerpt, seo, tags, reading
time and content hash are the translated half. The app merges them at read time, dropping any entry
the locale has no copy for rather than filling it in from English.

**Two things stay front-end published, on purpose.**

_Projects and testimonials_ are per-locale but are not Markdown: a project's localized title,
description and tags are locale MAPS inside its own `config.json`, and testimonials are a per-locale
JSON file in the content package. Neither is in the corpus i18n mirrors, so publishing them from
there would mean teaching it a second authoring format it has no source for.

_Search indexes_ are the one case where the split does not apply. Their CONTENT is entirely
translated, but their MEMBERSHIP is structural: the articles index contains only `listed` articles,
and `listed` comes from English config. An index i18n built would either omit that filter or need a
fact it does not hold. The builder still moved into `@jiki.io/content-renderer`, because a lunr
index is a serialised structure whose bytes depend on the lunr version, field order and boosts, so
if it ever does move the bytes are already contractual.

Single-writer per object holds throughout: `static:upload` excludes exactly the pointers i18n owns
(`i18n/*`, `exercises/*`, `concepts/*`, `content/copy/*`) and uploads the ones this repo owns.

**Frontmatter parsing is now part of the contract too.** It deliberately was not, while frontmatter
never reached the rendered HTML. The copy artifacts carry `seo` (a nested mapping) and `tags` (a
sequence) straight from frontmatter into content-hashed bytes, so a minimal reader that returned
those as strings would put the artifact at a different hash. `parseFrontmatter` lives in the shared
package and both repos use it.

**Two tests hold this in place**, in `tests/unit/lib/i18n/`. `unknownLocale.test.ts` drives every
namespace with a locale absent from every compiled manifest and requires each to read that locale's
pointer and then fetch what it named. `bundled.test.ts` is static, because a runtime test only
covers paths someone thought to call: it fails on a generated per-locale blob, on any import of one,
and on any module reading a hash manifest without going through the resolver.

## The Locale Roster Is Still Compile-Time

`ALL_LOCALES` in `lib/locales.ts` is a literal, and `Locale` is derived from it. Every locale's
CONTENT is fetched, but the list of which locale codes exist is not, so serving a genuinely new
locale code still needs a one-line front-end change and a deploy. Routing, `<html lang>` and `dir`
all read that list, and middleware needs it synchronously.

## The Exercise Cache: Prose and Code Are Separate Artifacts

An exercise has two kinds of cached content, and they vary along **different axes**:

- **Prose** (instructions) is translated, so it varies by locale and not at all by programming
  language.
- **Code** (stub, solution) varies by programming language and not at all by locale. The corpus
  contains exactly one `stub.javascript` per exercise and no per-locale variant of any code file.

They used to share one artifact keyed by `(slug, locale, language)`. That duplicated identical code
bytes into every locale, and, far more importantly, made translated instructions **unpublishable on
their own**: the `i18n` repo cannot emit an artifact that must also contain code it does not hold.
That single fact blocked the largest content type in the migration.

They are now separate artifacts on their real keys:

```
/static/exercises/{locale}/index-{hash}.json            prose index: [{slug,title,description,proseHash}]
/static/exercises/{slug}/{locale}/prose-{hash}.json     { instructions }
/static/exercises/code/{language}/index-{hash}.json     code index: { [slug]: hash }
/static/exercises/{slug}/code/{language}/code-{hash}.json  { stub, solution }
```

`code` is a reserved path segment and can never be a locale.

**Ownership follows the split.** The `i18n` repo publishes the prose index and the prose artifacts
for every non-English locale, plus the index's `current.json` pointer. The front-end owns English
prose and every code artifact outright. The prose index deliberately carries **no code hashes**: an
artifact one publisher owns must never need a fact only the other knows.

**What the client fetches.** `fetchExerciseContent` fetches the two indexes concurrently, then the
prose and code files concurrently, so the request chain is the same two levels deep it always was.
The split adds one request per level, not one round trip, and both indexes are cached for the
session. In exchange, code is fetched once per language rather than once per `(locale, language)`,
so switching UI locale re-fetches prose alone.

**Non-English index hashes are resolved at runtime** through `lib/i18n/catalogPointer.ts`, exactly
as the app and level catalogs are. English's hash is compiled into the worker and its artifacts ship
with the deploy, so the default-locale path does no pointer lookup at all.

**Local dev pointers.** `generate-exercise-cache.js` also writes a `current.json` for each
non-English locale it generates, so `pnpm dev` serves translated exercises with no `i18n` checkout.
Those are **excluded from `static:upload`**: on R2 the `i18n` repo is the single writer of every
non-English pointer, and two writers of one mutable object is the race the pointer design exists to
prevent.

## Prose Rendering: `@jiki.io/content-renderer`

Every piece of Jiki prose (concept pages, exercise instructions, and posts: blog, articles and
guides) is rendered by `@jiki.io/content-renderer`, a package in this monorepo at
`content-renderer/` that is also **published to npm**. It is the only package here that goes to the
registry.

**Why it is a package rather than a module.** English prose is authored here; its translations live
in the separate `i18n` repo. Both publish to the same content-hashed R2 tree, where an artifact's
filename **is** the hash of its bytes:

```
/static/concepts/{slug}/{locale}/content-{hash}.html
```

The two repos therefore have to render byte-identical HTML for identical input, not merely similar
HTML. One character of difference moves the hash, and the front-end then resolves a URL nothing was
ever written to, so the page silently does not appear. Two implementations would drift and the
drift would surface as a wrong-looking page rather than as an error. **The package version is the
contract**: both repos pin an exact version, and a rendering change is a version bump both sides
take deliberately.

**Two renderers, not one.** The package holds two configured pipelines, because Jiki's two prose
families genuinely disagree and merging them would rewrite the bytes of a published corpus:

|               | concept pages (`renderMarkdown`)          | posts (`renderPost`)                                             |
| ------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| footnotes     | no                                        | yes, via `marked-footnote`                                       |
| grammars      | `jikiscript`, Jiki's own `javascript`     | stock `html`/`xml`/`css`/`javascript`/`js`/`bash`/`shell`/`json` |
| unknown fence | escaped by hand into a bare `<pre><code>` | handed to `marked`'s own default                                 |
| images        | none                                      | `/images/...` rewritten to fingerprinted URLs                    |

The rule the package enforces is not "one renderer". It is that **no configuration of `marked` or
of `highlight.js` exists anywhere else**. Both libraries configure by global mutation, so a second
copy is not a duplicate, it is a race.

**What is in it.** `renderMarkdown`, `renderPost`, `prepareInstructions` (the trim and the
inline-tag strip, for instructions, which are cached as Markdown and rendered in the browser),
`rewriteImageRefs`, `postImageUrl`, `stripInlineTags`, `contentHash`, and `RENDERER_VERSION`.
Anything that can move a byte is part of the contract, so `marked`, `marked-footnote` and the
grammar packages are pinned exactly rather than ranged.

`renderPost` takes an injected `resolveImage`, because resolving an image reference to bytes is the
one part that legitimately differs: the front-end reads and copies them from the `content` package,
while `i18n` only names images the front-end has already published. The URL SHAPE is in the package
(`postImageUrl`), because it lands inside the HTML whose hash is its filename.

**Who uses it here.** `scripts/generate-concept-cache.js`, `scripts/generate-content-cache.js` and
`scripts/generate-exercise-cache.js`. All three formerly configured Markdown inline.

**Not in it.** Project episodes still render through `generate-content-cache.js` using `renderPost`,
but they are not published from `i18n`: their source layout (a UUID directory that is not the slug,
metadata in a per-episode `config.json`) does not fit that repo's `(type, locale, slug)` coordinate
system.

**Pinning `marked` is load-bearing, and was already nearly wrong.** The package originally pinned
`marked` at `17.0.1` while the app resolved `^17.0.1` to `17.0.6`. Those two versions differ in
whether image `alt` text is HTML-escaped, which silently changed one rendered post. The pin is now
`17.0.6`, matching what production serves. Concept output is identical under both, so the pin was a
latent landmine rather than a live divergence, but it is precisely the failure mode the package
exists to catch.

**Note on scope.** The package is `@jiki.io/content-renderer`, matching the npm org `jiki.io`. The
monorepo's other packages are `@jiki/*`. They are workspace-only and unpublished, so their scope has
never had to correspond to a real npm org; nothing depends on the two scopes matching.

**The `<define>`/`<literal>` convention.** Authored English may carry `<define>` and `<literal>`
inline tags. They are authoring markers, not output, and are stripped (keeping their inner text)
before anything is hashed. Translated files arrive tag-free, so the strip is a no-op for them.

## Adding a New Locale

When adding a new locale, you must:

1. Add the locale code to `ALL_LOCALES` in `lib/locales.ts` (canonical BCP-47 casing, e.g.
   `pt-BR`)
2. Add its message catalog `messages/{locale}.json` (structurally identical to `en.json`)
3. Add the curriculum level catalog `curriculum/src/levels/locales/{locale}/translation.json`
   (same key tree as `en`; use the `�` placeholder for anything untranslated)
4. Add translated content markdown files in the content package
5. **Generate a search index for the new locale** - The content generation script automatically creates search indexes per locale at `public/static/content/search/{type}/{locale}/index-{hash}.json`. Run `pnpm run content:generate` after adding content.
6. **If the locale is right-to-left** (Arabic `ar`, Hebrew `he`, Persian `fa`, Urdu `ur`, ...), add its code to `RTL_LOCALES` in `lib/locales.ts`. This drives `dir="rtl"` on `<html>` via `getLocaleDirection()` (server-rendered in `app/layout.tsx`, synced client-side on locale swap in `ClientLocaleProvider`). The code editor and the visual exercise canvas stay `dir="ltr"` (LTR islands). Omitting this leaves the UI left-to-right for that locale.

## Search Indexes

Article + guide search indexes are generated at build time, one per type per locale
(content-hashed, served immutably from R2):

- `public/static/content/search/articles/{locale}/index-{hash}.json`
- `public/static/content/search/guides/{locale}/index-{hash}.json`

These are automatically created by `scripts/generate-content-cache.js` when content is generated. When adding a new locale with articles, the corresponding search index will be created automatically.
